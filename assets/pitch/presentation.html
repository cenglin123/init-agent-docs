init-agent-docs

为项目构建“Agent 优先”的文档体系

三大核心设计哲学

1. 给地图，不给百科

AGENTS.md 在上下文中始终驻留，每一行都在消耗注意力预算。

控制在 100 行以内，只放指针不放细节。

2. 渐进式披露

先给地图
(AGENTS.md)
↓
按需探索细节
(docs/*.md)

3. 独立验证视角

执行者刚写完代码立刻自检，天然带有确认偏误。

计划中必须给“复查”留位，优先使用新视角验收。

信息分层结构

AGENTS.md行为规则 (驻留, ~100行)
docs/STRUCTURE.md文档总索引 (导航表)
docs/*.md深度文档 (API、部署、陷阱)
docs/plans/执行计划 (跨会话协议)

文档维护：记什么与不记什么

✅ 必须记录 (代码里读不出的)

  • 设计原因 (Why 选用某技术)
  • 协作约束 (团队约定与规范)
  • 环境陷阱 (坑位经验与解法)
  • 基础设施 (部署与环境约定)

❌ 绝对不记 (代码/Git 已有的)

  • 目录结构 (ls 一下就知道了)
  • 模块职责 (读代码就知道了)
  • 函数签名 (IDE 里都能看到)
  • Git 历史 (git log 即可查阅)

计划：跨窗口协议

计划是 Agent “失忆”后的救命稻草。
  • 现状：哪些阶段已完成？
  • 目标：当前该做哪个阶段？
  • 上下文：前人留下了什么问题？

计划：状态与颗粒度

黄金法则

一个阶段涉及 5-10 个文件 的修改最合适。

状态流转：
queue → claimed → in_progress → review → ✅ completed

目标文件结构

├── AGENTS.md (主文件)
├── CLAUDE.md / GEMINI.md (硬链接)
├── docs/
│   ├── STRUCTURE.md (总索引)
│   ├── CHANGELOG.md (变更历史)
└── docs/
    ├── CURRENT.md (状态)
    └── plans/ (执行计划)

工作模式选择

模式适用场景最低文档
直接执行小修改/低风险AGENTS + CURRENT
分阶段中等复杂度上述 + plans
并行协作高风险/多 Agent上述 + 分配表

必须避免的反模式 (1-6)

1. 巨型 AGENTS

挤占窗口。解法：内容下沉到 docs/。

2. 重复代码信息

导致腐烂。解法：绝对不记 "What"。

3. 缺少完工检查

导致漂移。解法：机械化执行清单。

4. 计划仅在对话

压缩即丢。解法：必须落盘到计划文件。

5. 执行即验证

存在偏误。解法：增加独立复查视角。

6. 写日志读全文

浪费 Token。解法：使用 scripts/changelog.py 查看标题树和局部内容。

仓库是唯一的记忆

文档是 Agent 跨越会话的唯一纽带。

# 设计依据与维护边界

## 地图与事实源

AGENTS 是精简的行为入口，不是百科；渐进披露只在需要时展开专题。约束/命令有唯一权威位置，少写代码或正文可直接推导的清单。Small 文件治理内联；中大型归 STRUCTURE。可执行事实优先，旧 instruction 读取后迁移，不能靠模板覆盖用户事实。

初始化与恢复本身也消耗上下文；阶段进度落盘，先最小安全入口后补专题，状态不重复抄到 CURRENT。拆文件不等于释放上下文，阶段以可交接/可验证为界，不规定文件数。

## 模型与机制

Occam：如无必要，勿增实体。Bitter Lesson 在这里指导优先使用通用模型能力，不能把工程外推当作原论文已证明的结论。Agent 决定语义、分解、协作和提示词；脚本承载确定性顺序、记账、路由、验收与止损。

区分封顶型先验（枚举未来任务知识、固定组织/模型/拓扑）与防呆型机制（契约、预算、过程监督）。机制不执行任务本身、不收窄可达解空间，留真实逃生舱；机械契约违反 fail-closed，判断分歧 fail-open，后者仍服从现有授权。不得借逃生舱扩大权限。

## 独立评审等级与标定


同一个 Agent 在同一个上下文窗口里做完实现，再立刻说"我已经验证过了"，天然带有确认偏误。它刚写完代码，最容易忽略自己埋下的问题。

因此文档体系里应显式给"验证"留位置。**分级判据是文件性质，不是改动行数**——治理文档改 2 行的连锁影响可能远超业务代码改 200 行：

- **治理文档**：无论改动规模，必须由独立视角复查。理由是确认偏误对此类文件最为致命：执行者在同一上下文里刚写完规则，天然看不到其中的歧义和盲区，而一条模糊规则在后续几十次会话中被错误解读的连锁成本远超一轮 converge spawn 的开销。
  - **判定范围**：AGENTS.md、SKILL.md、预提交 hook、审计脚本，以及任何被 Agent 作为行为规则消费的文件。识别辅助：若文件被 AGENTS.md 引用为规则执行工具（如 pre-commit hook、audit.py），或被框架自动加载（如 `.claude/settings.json` 中的 hooks、opencode 的 `~/.config/opencode/plugins/*.js` 插件），即属于治理文档。
  - **独占性**：治理文档层是独占判定——一个改动只要触及治理文档，就按本层规则处理，不叠加或降级到下层（高风险/中等风险/低风险）。若同一任务同时触及治理文档和业务文件，仅治理文档部分按本层复查，业务文件部分按原有分级独立判断——两个部分可分别走不同的审查流程。
  - **ultraverge vs 标准 converge**：
    - **ultraverge**（≥3 Reviewer）：涉及新增、删除或重定义**准则段**。准则段是文档中规定行为规则、禁止事项或判断标准的段落——区别于导航表、信息指针和示例性说明。判定以段落的首要功能为准：约束速查表（禁止/替代）的首要功能是规则，属于准则段；纯导航指针（如"文档总索引：[docs/STRUCTURE.md]"）不属于。若一段落同时含规则和指针，以主导功能判定。
    - **标准 converge**：其他治理文档修改（如调整导航表、增补说明性文字、修正交叉引用）。
  - **初始化豁免**：AGENTS.md 通过本 skill 初始化（而非后续自发修改）时，初始化独立入口检查的单次 reviewer-perspective 复查已充分——初始化是模板化操作，不同于对已有治理文档的自发修改；初始化不触发 ultraverge。
- **高风险 / 跨模块改动**：必须由独立视角复查（新上下文窗口、subagent 或人类 reviewer），不接受执行者自检。
- **中等风险**：建议换视角，至少在 compact 后以 reviewer 视角自查一次。
- **低风险（小修改、纯文案、纯样式）**：执行者自检即可，但仍要走完工检查清单。

无论哪个层级，计划模板和完工清单都应保留 `review` 这一状态，让人类知道这里存在一个明确的审批点，而不是默认"执行完就算完成"。

**评审质量需要标定，而不只是计数**：独立评审的行记录只回答"评审发生过"，不回答"评审是否看得懂"。触发键不取首轮结论：**治理文档的独立评审必标定**（已有同一基线的 ≥3 个独立视角时视角互证已足，豁免优先；同上下文/同模型的重复审查不计入互证），其余单评审按项目自定的每 N 次抽 1 次。标定做法：补派一名独立评审人严格盲评——只给冻结基线（固定 diff 或补丁哈希），不给首轮结论、不读取首轮评审记录；"无实质问题"仅作比对口径（无 P1/P2 且无改变行为或判据的 P3；纯文风与建议不计），不作触发条件。一致与分歧记入计划完成记录或 CHANGELOG（注明基线、评审者数、结论），分歧按本节评审等级复查；一致性只作趋势观测，不得作为放行或免审依据。初始化自检不适用标定（其余场景不得以自查替代独立评审）；发现项数量不影响触发。

## 维护与治理

治理合同是自维护、自治理和提案式进化的唯一通用源。确定性修复用适用检查与既有评审；行为/约束改变冻结候选、基线和验收。机械通过不保证语义正确；候选不自己裁通过、不抹失败、不无限递归。

治理正文写最终态；过程归计划/版本历史/CHANGELOG。CHANGELOG 用脚本 titles/show/add/recent 局部操作，不读全文；CURRENT 只存当前状态，复杂任务用计划交接。派生索引由维护器写，Agent 写经验内容；记忆活性年龄仅为线索，不能以无意义修改销警。pitfalls 同一坑再次发生且无 bugfix 档案时升格为带证据档案；经验晋升内联摘要与此不同。

发现断言与实机不符：先复现并对照可执行事实，无法判定则登记债务；修正后治理文档仍独立复查。核对本文档同维度断言及跨文档同源断言（命令、接口成功判据、UI坐标、字段语义、脚本与规则行为）；无法归类排除项逐条列出。同维度失效≥2、总失效≥3或涉及决策/环境，转全量审计。超出项目约定核对预算的未核项登记「文档+维度+未核数」。局部结论写任务记录/CHANGELOG，不写审计记录日期销警；债务段在审计记录之前。

hooks/CI 只能覆盖其实际触发路径；pre-commit 可绕过，读入入口也不保证模型遵守。会话级提醒属半硬约束：脏区检测与注入为机械事实，处置属判断，无宿主扩展点则如实说明软约束。不能伪造覆盖。

KB 领域机制不复制到普通代码项目；无论有无控制器，均保持独立验收、权限和预算边界，不依赖未安装全局 Skill。
